重组和@Composeable

@Composable

被@Composable标记的方法，它叫“可组合函数（Composable Function）”。

它是一个静态的、描述性的 UI 生成模板。被它标记的代码，在编译时会被 Kotlin 编译器插件（Compose Compiler）疯狂“魔改”，在函数的参数列表里偷偷塞进一个叫 composer: Composer 的隐式参数。

它负责的是：“告诉我当前应该画什么 UI”。

重组

重组不是一个方法，而是一个由 Compose Runtime（渲染引擎）发起的“动作”。

当某个mutableStateOf的值发生改变时，Compose Runtime 内部会调度一个任务。这个任务会圈定受到影响的、最小的 @Composable 函数范围（被称为 RecomposeScope）。

Compose 快照系统与 mutableStateOf 底层原理剖析

Compose于数据内容绑定的流程

通过下面一个可组合函数进行原理分析:

  • 重组范围的诞生：
    编译器会为该区域生成一个 RecomposeScopeImpl 对象（即重组作用域），它本质上是一个能够记住**”如何重新执行自己这部分 UI 图纸”**的闭包包装器。

  • 上下文隐式传导：
    在 Counter() 开始执行同步 Message 循环时，Compose Runtime 会首先创建一个 MutableSnapshot（假设 ID = 100），并将其通过 SnapshotThreadLocal.set(snapshot) 绑定到当前主线程上。此时，该快照中的 readObserver 闭包会被动态挂载为当前 Counter 的重组监听雷达。

  • 依赖绑定：
    当执行到 if (count.value < 2) 时，触发了 count.value 的 get() 操作。底层会通过 SnapshotThreadLocal.get() 拿到当前快照及雷达（readObserver），从而将 Counter 的 RecomposeScopeImpl 成功注册到该状态的观察者名单中。

mutableStateOf、StateRecord 与 SnapshotThreadLocal的关系链

在内存结构中，mutableStateOf 并不是一个存储单一数值的普通变量格子，而是一个遵循 软件事务内存（STM） 架构的“多版本账本”。它们四者的交互关系链如下：

        Record2["Record 2<br/>【历史线上版本】<br/>标签: 上一次提交的版本号<br/>数据: 历史线上值<br/>✅ 全局可见"]
        Record1["Record 1<br/>【初始版本】<br/>标签: 系统启动初始版本号<br/>数据: 初始默认值<br/>🌍 全局可见"]
    end

    StateObj -->|持有头指针 firstRecord| Record3
    Record3 -->|next 指针| Record2
    Record2 -->|next 指针| Record1
  • **mutableStateOf (StateObject)**：
    对外暴露的状态容器（总账本）。本身不存数据，只维护一个链表头指针 firstRecord。
  • StateRecord：
    链表中的独立版本节点（账本的某一页）。包含该版本的真实数值 value 以及创建它的 snapshotId。
  • Snapshot：当前的事务环境（透视眼镜）。包含当前统一的 id 以及用于精准依赖收集的 readObserver 闭包。
  • SnapshotThreadLocal：线程隔离的路由器。充当隐式传送门，让当前线程的代码在不显式传递参数的前提下，随时能 get() 到当前的 Snapshot 事务机。

🔄 微观时序三步走：

  1. 【读】依赖收集与精准绑定

    • 编译期魔改：编译器为 @Composable 块生成一个 RecomposeScopeImpl（重组作用域闭包）。
    • 眼镜导航：主线程启动重组 Message，创建 Snapshot(ID: 100) 并存入 SnapshotThreadLocal。
    • 查询可见性：执行 count.value < 2，根据快照 ID 100 遍历链表，过滤掉未提交的/大于 100 的节点，寻找到小于等于 100 的最大 ID 节点（返回 0）。
    • 收集：将当前的 RecomposeScopeImpl 闭包动态挂载到快照的 readObserver 中，完成绑定。

  2. 【写】“草稿纸”机制防御同步死循环

    • 现场分叉：执行 count.value++，系统发现链表头不是 100。为了防止直接改动数据导致同步嵌套调用（引发栈溢出死循环），系统在内存中克隆（Clone）一个新 Record，打上 snapshotId: 100, value: 1 标签，插到链表最头部。
    • 延迟通知：此时绝对不发送重组通知，仅仅更新链表。
    • 写后读：执行 print 再次读取时，带着 ID 100 的凭证在链表头直接匹配到 snapshotId: 100，故能精准读到最新的 1。

  3. 【退出】事务提交与异步入队

    • 可组合函数执行完毕，关闭快照并执行 snapshot.apply() 提交事务，此时修改正式并入全局可见视角。
    • 快照系统盘点本轮变更，调取第一步存下的观察者闭包，通过 Handler.post 异步将“触发下一轮重组”的消息推入主线程 Looper 队列尾部。
    • 主线程本轮 Message 安全释放，在下一个事件循环里安全重组，彻底隔离了死循环。

3. 为什么必须设计成“链表形式”？

如果只在主线程，延迟通知确实能防死循环，但链表（MVCC 多版本并发控制）是为了解决以下单靠延迟通知无法处理的致命场景：

  • 多线程读写隔离（防 UI 撕裂）：后台线程异步修改 State 时，只是往链表头插它自己的新 ID 节点。主线程因为 SnapshotThreadLocal 锁定了当前的快照视图，会直接过滤掉后台干扰，实现读不锁写、写不锁读。
  • 事务回滚（废弃重组）：若重组进行到一半因用户滑动屏幕而无意义废弃，挂在链表头的临时快照 Record 会被直接丢弃或 GC 回收，数据瞬间完美回滚，绝不污染全局数据格。
  • 未来特性支持：为 Compose 未来提升多核性能的并行重组（多线程同时重组不同 UI 树片段）提供底层底座支持。
